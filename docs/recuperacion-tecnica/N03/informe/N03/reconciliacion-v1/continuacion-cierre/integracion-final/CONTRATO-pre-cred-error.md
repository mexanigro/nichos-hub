# Pipeline HTTP integrado antes de reparar autoridad

Decisión aprobada: clients/config/payment_credentials de esta API proceden del backend de citas, conservando navegador separado. No bypass ni excepción de guarda. Middleware debe rechazar suspended/archived y ausencia/inválido/error/timeout antes de rutas. Este contrato no cambia reglas ni políticas de roles.

Población fija r2: 23 casos por runtime. Viaje objetivo coincidente y separado POST book → GET CRM de la misma cita → PATCH del mismo documento → checkout con seña config2500 ILS. **No se inserta precio artificial en esa cita.** El esperado checkout200 permanece y será RED si book no deja precio autorizado. El primer instrumento añadía15000 como fixture; se preserva el corte histórico, pero ese positivo NO acredita la conexión real book→checkout. La corrección del montaje retira un prerrequisito artificial y no rebaja el objetivo.

Otros casos conservados: trial, suspended, archived, estado ausente/inválido/error/timeout, origin ajeno, ausencia auth, membresía otrotenant, body>32kb y segunda petición rate limit. Población prepriced SEPARADA: cita preexistente con priceCents15000 para aislar provider manual/none/invalid/null/vacío frente a ausencia con legacystripe/none, configerror y destinos separados. None/manual rechazan antes de resolver; invalid/null/vacío/error no producen gateway. Ausencia admite legacyválido; configerror no permite fallback del runtime. Clients/config/credentials positivos deben leerse efectivamente del namespacebackend. Estos controles prepriced nunca se atribuyen al precio generado por book.

Se extraen todos los seis middleware aplicables a estas rutas en orden AST: securityHeaders, express.json, requireTrustedOrigin, rateLimit, attachTenantContext, enforceClientActive. /api/ai no aplica al path. Luego registros reales de book, GET/PATCH CRM y checkout. Funciones/accessors SDK reales; tokenRSA/lookup reales; DB pornamespace e I/O interceptados. Resolver real de provider/credenciales; sólo builder/transporte final sustituido. REST helper de lookup de membresía se intercepta en su límite collection/id, con lookup real tenant/rol.

Oráculos fijados antes de primer resultado/producto runtime. P0 RED alcanzable→P1 reparación autorizada→P2 GREEN y mutantes bypass-tenant/reject-valid en memoria→revisión local. Mutantes no cambian expectativas ni producto. Requests/trace/writes/resultados conservados. Sin startup entero, proveedor, reglas, concurrencia o SDK remoto; este montaje acredita la cadena local explícita, no todos los endpoints del repositorio.

Refutación de precio: el handler book actual guarda customer/service/status y datos de turno, pero no priceCents/price; BookingWizard sólo manda su estimación después a checkout, donde debe ignorarse. Falta una autoridad de catálogo/precio backend para producir una cita cobrable sin confiar en body. No se implementa esa política por inferencia ni se declara el checkout operativo por la población prepreciada. Decisión y alcance de esa reparación pendientes del integrador.
